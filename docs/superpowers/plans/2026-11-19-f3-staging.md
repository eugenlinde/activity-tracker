# F3 Staging Implementation Plan

**Goal:** Every pull request from this repository runs on a second copy of the app on the same server after green checks, and the PR is told.

**Spec:** GitHub issue #22 (approved by the developer 2026-11-19).

**Architecture:** Staging is the production compose file run a second time under another project name, from its own directory with its own `.env`. Production's proxy also answers for the staging address and passes those requests to the staging `web` container over one shared Docker network. A second SSH key, limited on the server to one script, lets CI ask for "this tag on staging" and nothing else.

**Tech:** Docker Compose, Caddy, bash, GitHub Actions. No new tools.

## Global constraints

- The staging address, the server address and e-mail addresses are never written into repo files: they live in the server's `.env` files and GitHub secrets.
- Scripts never print a secret and never use `set -x`.
- Fork PRs get no secrets and never deploy.
- Nothing staging does may read production's database, files or `.env`.
- Staging uses the compose files that production currently runs (from `main`), never a compose file from the PR. Only the images come from the PR.
- No comments in scripts or workflows.

## Files

| File | Change |

| `infra/provision-staging.sh` | new: run once as root. Staging directory and `.env`, the shared network, `STAGING_ADDRESS` into production's `.env`, the restricted key line |
| `infra/test/run.sh`, `infra/test/stubs/*` | tests for all of the above |
| `.github/workflows/ci.yml` | `images` also builds for same-repo PRs; new `staging` job; prod `deploy` ships the two new files |

| `docs/ARCHITECTURE.md`, `.claude/*` | the staging section, roadmap, decisions |

## Interfaces

- `staging.sh` reads `SSH_ORIGINAL_COMMAND`. Accepts exactly `deploy pr-<number>-<40 hex> <number>` (the two numbers equal) or `reset`. Works in `STAGING_DIR` (default `/opt/tracker-staging`), copies `compose.yml`, `compose.staging.yml`, `deploy.sh` from `TRACKER_DIR` (default `/opt/tracker`) before a deploy. Prints `result=deployed|rolled-back|failed|reset` and `previous-pr=<number or none>`. Exit status 0 only for `deployed` and `reset`.
- Staging `.env`: `COMPOSE_FILE=compose.yml:compose.staging.yml`, `SITE_ADDRESS=:80`, `HEALTH_URL=https://<staging address>/actuator/health`, `PREDEPLOY_DUMP=off`, own `POSTGRES_PASSWORD`, `JWT_SECRET`, `SIGNUP_ALLOWED_EMAILS`, placeholder OpenRouter values, `IMAGE_TAG=none`.
- Production `.env` gains `STAGING_ADDRESS=<staging address>`.
- Image tag for PRs: `pr-<number>-<head sha>`, built from the same merge ref the tests ran on.
- GitHub: environment `staging` with secrets `STAGING_HOST`, `STAGING_SSH_KEY`; variable `STAGING_ENABLED`.

## Rules pinned by tests

- `staging.sh` refuses anything but the two commands: other verbs, extra words, shell metacharacters, a tag that is not `pr-…`, a tag whose number differs from the PR number, an empty command. Nothing is run for a refused command.
- A deploy copies the three files from the production directory first, then runs the staging copy of `deploy.sh`; the previous PR number is reported and replaced only on success.
- `reset` removes the staging containers and volumes and nothing of production's.
- `deploy.sh`: the network is created when missing and left alone when present; `HEALTH_URL` from `.env` is used when set; no dump when `PREDEPLOY_DUMP=off`; without those lines it behaves exactly as before.
- `provision-staging.sh` is safe to run twice: an existing `.env` is left untouched, the key line and `STAGING_ADDRESS` are not duplicated.

## Review focus

1. Any way for the staging key, or for a PR that rewrote the workflow, to run something other than a staging deploy or reach production's directory.
2. Any path by which staging containers can reach production's database or files.
3. A staging failure (not started, out of memory, wrong upstream) taking production down.
4. Production deploys on a server where staging was never provisioned (must still work).
5. Secrets or addresses in logs, PR comments or repo files.

## Order of work

1. `Caddyfile`, `compose.yml`, `compose.staging.yml`; check with `docker compose config` and `caddy validate`.
2. `deploy.sh` changes, tests first.
3. `staging.sh`, tests first.
4. `provision-staging.sh`, tests first.
5. Workflows.
6. Rehearsal on the laptop: production and staging side by side with locally built images.
7. Whole-branch review by a fresh reviewer; fixes test-first.
8. Docs, PR.
9. After merge, with the developer's go-ahead: DNS record (developer), provisioning on the server, GitHub environment and secrets, switch on, the drills from the spec.
